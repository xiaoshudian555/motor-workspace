# Scaling 证明副本数变化机制按预期工作

## 负责

- 验证实例规模变化的触发链路、目标对象、收敛过程和服务可用性。
- 区分人工显式变更副本数与指标驱动自动变更副本数。
- 记录扩缩容前、中、后的 InstanceSet、HPA、Pod、Coordinator 注册状态和推理结果。
- 在副本数变化后引用 routing-topology 的判据，证明路由和流量分配已收敛。

## 子类

| 子类 | 证明什么 | 入口 |
|---|---|---|
| manual | 外部显式修改目标实例数后，系统能完成有意拓扑变化 | [`manual/`](manual/) |
| auto | 指标链路触发 HPA/Operator 自动调整副本数 | [`auto/`](auto/) |

## 完成标准

扩缩容触发条件、目标角色、目标副本范围、观测窗口和恢复/清理方式明确；副本数变化、
Coordinator 感知、推理可用和路由收敛均有证据。

## 不负责

- 单独寻找最大稳定负载或系统饱和点；该责任属于
  [`../stress-capacity/`](../stress-capacity/)。
- 单独证明请求一定路由到目标实例；该责任属于
  [`../routing-topology/`](../routing-topology/)，本场景只在副本数变化后引用其判据。
- 故障注入触发的隔离、降级、重拉起或被动恢复；该责任属于
  [`../reliability/`](../reliability/)。
- 用一次最终推理成功代替扩缩容链路证据。

## 交付

`scaling` 证据目录包括配置/策略摘要、触发动作、时间线、K8s 对象状态、
Coordinator 状态、请求结果、路由收敛证据、失败倒查入口和清理结果。
